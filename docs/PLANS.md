# 기능 계획

작성: 2026-11-09 · 구현 전 계획이다. 이 문서의 내용은 아직 빌드·인게임 확인을 거치지 않았다. 진행 순서는 **1. 측후 표시 → 2. 감정표현 맞추기**다.

API 존재 여부는 고정 컴파일 참조 wasdcxz15.0.3.7의 Dalamud.dll/FFXIVClientStructs.dll을 리플렉션으로 확인했다. 실제 동작(값 의미·타이밍·색 형식)은 각 기능의 조사 단계에서 인게임으로 확인해야 한다.

## 1. 측후 표시 (Positional FlyText)

### 목표

측면·후방 조건이 있는 내 스킬이 맞았을 때, 화면에 뜨는 데미지 텍스트(예: `화차 ⚔ 31583`)를 성공·실패에 따라 다르게 보여 준다. 성공 여부는 위치 계산으로 추정하지 않고 **서버가 보낸 스킬 결과**로 판정한다.

### 표현 방식

원칙: 기존 파판 데미지 텍스트 스타일을 유지하고 붕 뜨지 않게 한다. 글자·기호·크기는 그대로 두고 **색만** 바꾼다.

| 결과 | 표시 |
|---|---|
| 성공 | 게임 UI 색상표(UIColor 시트)의 따뜻한 강조색(금색 계열)으로 텍스트 색 변경 |
| 실패 | 게임의 "효과 없음/저항" 텍스트와 같은 계열의 흐린 회색으로 변경 |
| 판정 불가 | 변경 없음(게임 기본 표시) |

- 대상은 **내가 쓴 측후 조건 스킬의 데미지 텍스트**만이다. 자동 공격·도트·다른 스킬·다른 사람의 텍스트는 바꾸지 않는다. 따라서 측후 스킬 텍스트의 색이 평소와 다르면 성공, 흐리면 실패로 읽힌다.
- 스킬명에 문구를 덧붙이지 않는다. 극대·직격의 글자 크기·느낌표, 아이콘, 종류(kind)도 게임 기본 연출 그대로 둔다.
- 색은 임의 RGB가 아니라 게임 UIColor 시트에 있는 값 중에서 고른다. 기본 데미지 색과 구분되면서 튀지 않는 값을 인게임에서 비교해 확정한다.
- 진북 상태에서는 서버가 성공으로 처리하므로 성공으로 표시된다(조사 단계에서 확인).
- 판정값을 해석하지 못했거나 대응하는 결과를 찾지 못하면, 실패로 단정하지 않고 원래대로 둔다(Unknown 원칙).
- PvP에서는 동작하지 않는다(측후 조건이 PvE 스킬 기준).
- 설정 항목:
  - 기능 켜기/끄기(기본 꺼짐).
  - "실패도 표시"(기본 켜짐).
- 채택하지 않은 방식:
  - 스킬명 뒤 문구(`· 후방`, `· 측후 실패`): 원래 텍스트에 없는 요소라 튄다.
  - 별도 큰 글자 팝업(`AddFlyText`): 화면이 복잡해지고 원래 텍스트와 시점이 어긋난다.
  - 효과음: 게임 소리와 섞여 구분하기 어렵다.
  - 위치 기반 추정: 서버 판정(히트박스·지연)과 어긋날 수 있다.

### 구조

- **Core**(게임 비의존)
  - `PositionalActions`: 측후 조건 스킬의 ActionId → 요구 방향(측면/후방) 표.
  - `PositionalJudge`: 효과 바이트(Type, Param0~4, Value)를 받아 `Success / Failure / Unknown`을 돌려주는 순수 함수.
- **Plugin**
  - `ActionEffectHandler.Receive` 훅: FFCS가 해석한 함수 주소를 쓴다(실행 파일 SHA 검사 대상이 아니다). 처리 조건은 다음과 같다.
    - 시전자 = 내 캐릭터, ActionType = Action, ActionId가 표에 있을 때만 처리한다.
    - 대상의 데미지 효과(Type 3)를 찾아 `(ActionId, 대상, 결과, 수신 시각)`을 대기열에 넣는다.
    - 원본 함수는 항상 호출하고, 예외는 잡아서 기능만 끈다.
    - 이 프로젝트에서 처음 쓰는 함수 훅이다. 공개 Dalamud 서비스에는 스킬 결과 이벤트가 없다.
  - `IFlyTextGui.FlyTextCreated`(공개 서비스) 처리:
    - 종류가 `Damage*`이고, `text1`이 대기열 스킬의 한국어 이름(Action 시트, 시작 시 캐시)과 같으며, 2초 안에 들어온 결과가 있으면 색과 `text1`을 바꾼다.
    - 이 이벤트는 텍스트를 화면에 그리기 전에 호출되므로, 바뀐 표시가 처음부터 뜨고 추가 지연은 없다.
    - 2초는 기다리는 시간이 아니라 연결 허용 범위다. 스킬 결과 수신부터 데미지 텍스트 생성까지의 간격(공격 동작의 적중 시점)을 덮기 위한 값이며, 실측 후 줄인다.
    - 대기열은 먼저 들어온 순서로 소비하고, 시간이 지난 항목은 버린다.
  - 지역 전환·기능 해제·dispose 시 훅을 해제하고 대기열을 비운다.

### 조사 단계 (구현 전)

1. **판정값 위치**
   - 개발용 로그로 내 데미지 효과의 Param0~4/Value/Header.Flags를 기록한다.
   - 나무인형에서 스킬마다 다음 경우를 비교한다: 정면 / 요구 방향 / 반대 방향, 콤보 있음 / 없음, 진북.
   - 로그 분석 도구들이 쓰는 "보너스 비율" 값이 이 패킷에서 온다고 알고 있지만 확인된 사실은 아니다. 콤보 보너스와 섞이는지도 함께 확인한다.
   - 측후 성공만 구분할 수 없으면 이 기능은 보류한다.
2. **측후 스킬 목록**
   - GameDataProbe에 오프라인 조사 명령을 추가한다. KR Action/ActionTransient 설명에서 측면·후방 조건 문구가 있는 플레이어 스킬을 뽑는다.
   - 뽑은 목록을 사람이 검토한 뒤 Core 표로 고정한다. 출처와 게임 버전도 함께 기록한다.
   - 2026-11-09 결과: 아래 "조사 진행 기록"을 따른다.
3. **데미지 텍스트 형식**
   - `color`의 바이트 순서(ARGB/ABGR)를 확인한다.
   - `text1`에 붙인 한글이 깨지지 않는지 확인한다.
   - 데미지 텍스트가 스킬 결과 수신 뒤 몇 초 안에 뜨는지(지연 효과 포함) 확인한다.

  - 헤더: ActionId·이름·SpellId·AnimationVariation·Flags.
  - 수신 시점의 콤보 상태와 진북 여부.

- 모든 데미지 텍스트의 인자(종류·값·text1/text2·color·아이콘·y)를 `[PositionalProbe] flytext`로 남긴다. 텍스트는 바꾸지 않는다.
- 원본 함수는 항상 호출한다. 훅 주소는 FFCS가 해석한 값이며, 해석에 실패하면 켜지지 않는다.

**테스트 절차**
1. 공개판을 해제하고 개발판을 로드한 뒤 `/dbtw probe`를 입력한다.
2. 나무인형에서 직업마다 측후 스킬을 각각 다음 경우로 친다.
   - 요구 방향에서 콤보를 이어서.
   - 반대 방향에서.
   - 정면에서.
   - 진북을 켜고 정면에서.
   - 콤보 없이 요구 방향에서(콤보가 있는 스킬만).
3. 위치는 로그가 자동으로 기록하므로 따로 적지 않아도 된다. 테스트한 대략적인 시각만 알려 주면 된다.
4. 끝나면 `/dbtw probe`로 끈다.

로그는 `%APPDATA%\XIVLauncherKR\dalamud.log`에서 직접 읽어 판정값 위치를 분석한다(KR 런처 경로).

#### 2026-11-09 인게임 로그 분석 (사무라이 Lv100, 나무인형)

19:08:23~19:09:13 사이에 사무라이로 수집한 72줄을 분석했다. 측후 성공 여부를 바로 알려 주는 비트는 없었다. 대신 **데미지 효과의 Param2가 "보너스 위력 비율"** 이었다.

| 스킬 | 위치(로그 추정) | 콤보 | Param2 | 툴팁 위력(Lv100) | (적용 위력 − 기본) / 적용 위력 |
|---|---|---|---|---|---|
| 사풍·진풍 | — | O | 53 | 기본 140, 콤보 300 | 160/300 = 53.3% |
| 화차(측면) | 측면 | O | 61 | 기본 160, 측면 210, 콤보 370, 콤보+측면 420 | 260/420 = 61.9% → 성공 |
| 화차(측면) | 정면 + 진북 | O | 61 | 〃 | 성공(진북 반영) |
| 월광(후방) | 측면 | O | 56 | 〃(후방) | 210/370 = 56.8% → 실패 |
| 월광(후방) | 정면 | O | 56 | 〃 | 실패 |
| 효풍 | — | 시작기 | 0 | — | 0 |

- 미터기(ACT)와 분석 사이트도 같은 패킷의 이 값(FFLogs의 `bonusPercent`)을 쓴다. 분석 도구는 이 값을 위력 표와 비교해 측후 성공을 센다고 알려져 있다(코드는 직접 확인하지 않음). 우리는 게임 안에서 같은 패킷을 처리 시점에 받으므로 정보량·시점 모두 같다.
- 값은 소수점 이하를 버린 정수다(53.3→53, 61.9→61, 56.8→56). 크리티컬·직격(Param0의 0x20/0x40)이나 풍월 같은 피해량 증가 버프는 이 값에 영향을 주지 않았다.
- 같은 값이 데미지 텍스트 이벤트의 `value2`로도 넘어온다(사풍 53, 화차 61, 월광 56, 효풍 0). `text1`은 스킬 이름이다.
- 따라서 스킬 결과를 가로채지 않고 공개 서비스 `IFlyTextGui` 하나만으로 판정할 수 있다.
- 데미지 텍스트는 스킬 결과 수신 후 0.4~0.7초 뒤에 생성됐다. 이벤트는 그리기 전에 호출되므로 표시 지연은 없다.
- 기본 데미지 색은 `0xFF0061E3`이다. ABGR로 읽으면 (227, 97, 0) 주황이라 게임 표시와 맞는다. 버프 종료 텍스트의 회색은 `0xFF454545`였다.
- 진북 버프 자체도 "내 스킬 결과"로 기록됐다(대상=나, Type 14). 측후 스킬이 아니라 판정 대상에서 빠진다.

**판정 방식(수정)**
1. 데미지 텍스트의 `text1`이 측후 스킬 이름과 같으면 그 스킬의 툴팁을 현재 레벨·직업으로 평가한다(공개 서비스 `ISeStringEvaluator`, 레벨이 바뀔 때만 다시 계산).
2. "위력 / ○○ 시 위력" 줄들에서 상태별 위력을 읽고, 상태마다 기대값 `floor((상태 위력 − 기본 위력) / 상태 위력 × 100)`을 만든다.
3. `value2`가 측후 조건이 들어간 상태의 기대값과 같으면 성공, 측후 조건이 없는 상태와 같으면 실패다. 둘 다 아니거나 양쪽에 겹치면 Unknown으로 두고 표시를 바꾸지 않는다.

이 방식이면 `ActionEffectHandler.Receive` 훅은 조사용 로그에만 남고, 실제 기능에는 쓰지 않는다. 앞의 "구조" 절에서 훅·대기열로 설계한 부분은 이 방식으로 대체한다.

**판정 형태: 상태 고정 후 예/아니오**
1. 콤보 연결, 효과 향상, 예리한 송곳니, 호랑이 공력, 명경지수는 내 클라이언트 상태로 확정한다.
2. 상태를 고정하면 기대값은 "측후 없음"과 "측후 있음" 두 개뿐이다. 측후 보너스가 붙으면 비율이 반드시 올라가므로 두 값은 항상 다르다.
3. 서버 값이 둘 중 어느 쪽과 같은지가 곧 측후 성공 여부다. 둘 다 아니면 미지의 위력 효과가 있다는 뜻이므로, 추측하지 않고 표를 보완한다.

이 방식이면 리퍼의 효과 향상/측후 겹침도 사라진다. 2차 로그 기준 Lv94+ 효수형의 기대값은 향상 있음이면 0/9, 없음이면 0/10이다. 효과 향상은 보너스가 아니라 기본 위력을 올리는 효과였다.

**숨은 플래그 확인**

## 2. 감정표현 맞추기 (Emote Sync)

### 목표

춤처럼 반복되는 감정표현을 하는 사람을 우클릭해 "따라하기"를 누르면, 그 사람 동작의 반복 시작점에 맞춰 같은 감정표현을 실행한다. 같은 메뉴에서 상대가 어떤 감정표현을 하는지도 보여 준다.

### 표현 방식

- 플레이어 캐릭터 우클릭 메뉴(`IContextMenu`, 입찰 기능에서 이미 사용 중)에 항목을 추가한다.
  - 상대가 반복 감정표현 중일 때만 `따라하기 · <감정표현 이름>`을 보인다. 이름은 Emote 시트의 한국어 이름이다.
  - 내가 실행할 수 없으면(미습득, 탈것·전투 등) 항목을 비활성으로 두고 이름 뒤에 `(사용 불가)`를 붙인다. 이 경우에도 감정표현 정보는 볼 수 있다.
  - 반복 감정표현이 아니면 항목을 넣지 않는다.
- 진행 상황과 실패는 내 채팅창에만 표시한다(`IChatGui.Print`, 서버로 보내지 않음). 예: `따라하기 대기 중…`, `상대가 감정표현을 멈춰 취소했습니다`.
- 이름표나 대상 정보창에 감정표현을 상시 표시하는 기능은 메뉴 방식을 써 본 뒤 필요하면 따로 검토한다.

### 동작

1. **메뉴 열 때**
   - 대상 `Character.EmoteController`에서 `IsInEmoteLoop()`와 `EmoteId`를 읽는다.
   - 내 실행 가능 여부는 `EmoteManager.CanExecuteEmote(id)`로 확인한다.
2. **클릭**: 대상 ObjectId와 EmoteId를 기억하고 대기 상태로 들어간다. 이후 처리는 Framework 업데이트에서만 한다.
3. **반복 시작점 관측**
   - 대상 `TimelineContainer.TimelineSequencer`에서 감정표현 반복 타임라인 슬롯의 `SchedulerTimeline.CurrentTimestamp`를 읽는다.
   - 값이 줄어드는 순간을 반복 재시작으로 본다.
   - 두 번 관측해 주기를 구한다. 타임라인 자료에서 길이를 직접 읽을 수 있으면 그 값을 우선한다.
4. **실행 시각**: 다음 재시작 시각에서 내 감정표현의 시작(인트로) 구간 길이를 뺀 시각에 `EmoteManager.ExecuteEmote(id, option)`을 호출한다.
5. **사후 확인**: 내 `EmoteController.EmoteId`가 바뀌었는지 확인하고, 실패하면 채팅창에 알린다.
6. **취소 조건**: 다음 경우에는 실행하지 않고 대기를 비운다.
   - 대상이 사라지거나 감정표현을 바꾸거나 멈췄다.
   - 내가 이동했거나 전투에 들어갔거나 지역을 이동했다.
   - 10초가 지나도록 반복 시작점을 관측하지 못했다.

### 한계

- 타이밍은 **내 화면 기준**으로 맞춘다. 다른 사람 화면에서는 각자 받는 시각이 달라 네트워크 지연만큼 어긋날 수 있다.
- 시작 구간이 있는 감정표현은 감정표현마다 길이를 확인해야 한다.

### 조사 단계 (구현 전)

1. 춤 계열 감정표현 몇 개로 다음을 확인한다.
   - 반복 타임라인이 들어가는 슬롯 번호.
   - `CurrentTimestamp`의 단위와 재시작 시의 동작.
   - `ActionTimelineKey`로 반복 구간과 시작 구간을 구분할 수 있는지.
2. `ExecuteEmote`의 `PlayEmoteOption` 인자를 확인한다(null 허용 여부, 대상 지정, 모션만 실행 옵션).
3. Emote 시트의 ActionTimeline 배열(반복/시작 구간)과 실제 타임라인의 대응을 오프라인으로 대조한다.
